# SAFETY — 삭제/정리/제거 안전 정책

이 앱에서 가장 위험한 부분은 **파일 삭제**다. 이 문서는 삭제·정리·프로그램 제거와 관련된 모든 코드의 **최상위 규칙**이다.
다른 문서와 충돌하면 이 문서가 우선한다. 의심스러우면 "삭제하지 않는 쪽"을 택한다.

## 1. 기본 원칙

1. **기본은 삭제하지 않는다.** 명시적으로 허용된 것만 삭제한다 (허용 목록 방식, 차단 목록만으로 판단하지 않는다).
2. **휴지통 우선.** 되돌릴 수 있는 방식을 기본으로 한다.
3. **미리보기 → 확인 → 실행.** 모든 삭제는 대상과 용량을 보여주고 사용자가 확인한 뒤에만 실행한다.
4. **방어 계층 2중 이상.** (a) UI 비활성화 (b) IPC 핸들러 재검증 (c) 삭제 함수 내부 최종 검사. 어느 한 계층이 뚫려도 다음 계층이 막는다.
5. **모든 삭제는 기록한다.** 시간, 경로, 방식, 결과를 로그에 남긴다.
6. **사용자의 문서/사진/영상 등 개인 데이터는 정리 대상이 아니다.** 앱이 자동으로 정리 후보에 올리지 않는다.

## 2. 안전도 4단계 정의

| 값          | 표시          | 의미                                                                         | 삭제 허용                                                                 |
| ----------- | ------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `safe`      | 🟢 안전       | 지워도 시스템/프로그램에 문제 없고, 필요 시 자동 재생성됨                    | 정리 기능으로 가능                                                        |
| `caution`   | 🟡 주의       | 지울 수 있으나 영향이 있음 (다시 다운로드, 로그인 풀림, 빌드 재생성 시간 등) | 사용자가 직접 선택 + 경고 문구 확인 시 가능. "원클릭 정리"에는 포함 안 됨 |
| `protected` | 🔴 보호       | 지우면 시스템/프로그램이 손상될 수 있음                                      | **불가.** 버튼 비활성, 코드에서도 거부                                    |
| `unknown`   | ⚪ 알 수 없음 | 규칙 없음                                                                    | **불가.** (탐색기에서 열기만 제공)                                        |

### 판정 규칙

- 규칙이 여러 개 매칭되면 **가장 구체적인 규칙**(경로 패턴이 더 길고 정확한 것)을 쓴다.
- 구체성이 같으면 **더 보수적인(더 안전하지 않은) 안전도**를 쓴다. 순서: `protected` > `unknown` > `caution` > `safe`.
- 폴더 안에 `protected` 하위 경로가 있으면, 그 폴더 자체를 통째로 삭제하는 것은 불가. 규칙에 정의된 **정리 대상 하위 패턴**만 삭제한다.
- 안전도는 규칙 DB에서만 온다. 코드가 "이름이 temp니까 안전"처럼 추측하지 않는다.
- 단, §3 하드코딩 보호 경로에 걸리는 항목은 규칙이 없어도 UI에 🔴`protected`로 표시한다 (삭제 불가 사실과 화면 표시를 일치시키기 위함. 설명은 "시스템/개인 폴더").

## 3. 보호 경로 (하드코딩, 규칙과 독립)

아래는 규칙 DB가 어떻게 되어 있든 **항상 삭제 거부**한다. `src/main/safety/protectedPaths.ts`에 하드코딩하고, 이 목록을 줄이는 변경은 사용자 승인이 필요하다.

### 3.1 경로 자체 및 그 하위 전부 보호

- `C:\Windows` 및 하위 전체 (단, §5의 정리 허용 하위 패턴은 예외로 정확히 열거된 것만)
- `C:\Program Files`, `C:\Program Files (x86)` 하위 (프로그램 삭제는 §6의 제거 프로그램 방식으로만)
- `C:\ProgramData` 의 Microsoft, 드라이버/보안 소프트웨어 관련 폴더 (규칙에 명시된 캐시 하위만 예외)
- `C:\Users` 자체와 `C:\Users\<사용자>` 루트
- 사용자 개인 폴더: `Documents`, `Desktop`, `Pictures`, `Videos`, `Music`, `Downloads`, `OneDrive` 및 하위 전체
- `C:\Users\<사용자>\AppData` 루트 및 `Local`, `Roaming`, `LocalLow` 루트 자체 (하위의 규칙 허용 캐시만 예외)
- `C:\Users\<사용자>\.ssh`, `.gnupg`, `.aws`, `.kube` 등 인증/키 폴더
- 브라우저 프로필의 **로그인/북마크/비밀번호/쿠키** 데이터 (캐시 폴더만 정리 가능)
- `C:\System Volume Information`, `C:\$Recycle.Bin`(휴지통은 앱의 "휴지통 비우기" 전용 API로만), `C:\Recovery`, `C:\Boot`, `C:\EFI`
- 드라이브 루트(`C:\`) 자체
- 시스템 파일: `pagefile.sys`, `hiberfil.sys`, `swapfile.sys`, `bootmgr`, `BOOTNXT`, `ntuser.dat*`, `*.sys` (Windows 드라이버 폴더 내)
- 이 앱 자신의 설치 폴더와 사용자 데이터 폴더

### 3.2 정규화 후 검사 (우회 방지)

삭제 요청 경로는 검사 전에 반드시:

1. 절대 경로화 + `path.normalize` + 대소문자 무시 비교.
2. `..`, 8.3 짧은 이름, `\\?\` 접두사, 슬래시 혼용 정규화.
3. **심볼릭 링크/정션 해석**: 실제 가리키는 경로(`fs.realpath`)로 한 번 더 검사. 링크 자체를 따라가 삭제하지 않는다 (링크는 링크만 제거하거나 건너뛴다).
4. 경로가 허용된 정리 루트 **안에** 있는지 확인(접두사 비교 시 경계 문자 `\` 확인. `C:\Temp2`가 `C:\Temp`로 오인되지 않게).
5. 환경변수는 앱이 실행 시점의 실제 값으로 확장한 결과만 신뢰한다.

## 4. 삭제 허용 조건 (모두 만족해야 삭제)

삭제 함수 `deleteTarget(path, mode)`는 아래를 **모두** 확인하고 하나라도 실패하면 거부 + 로그:

- [ ] 경로가 §3 보호 경로가 아니다.
- [ ] 경로가 규칙 DB의 `cleanable: true` 규칙의 허용 범위 안에 있다. (`cleanable: false`인 표시 전용 규칙은 `caution`이어도 삭제할 수 없다.)
- [ ] 규칙의 안전도가 `safe` 또는 `caution`이다 (`protected`, `unknown` 거부).
- [ ] `caution`이면 사용자가 경고 문구를 확인했다는 플래그가 요청에 있다.
- [ ] 정규화/realpath 후에도 위 조건이 유지된다.
- [ ] 요청이 "확인 단계"를 거쳤다 (확인 토큰 — ARCHITECTURE.md의 `confirmationId`).
- [ ] 영구 삭제 요청이면: 규칙 카테고리가 `temp` 또는 `cache`이고, 설정에서 영구 삭제가 허용되어 있다.

## 5. 정리 허용 예외 (보호 경로 안의 정리 가능 하위 경로)

보호 폴더 안이라도 아래처럼 **정확히 열거된 하위**는 규칙 DB를 통해 정리할 수 있다. (이 열거 목록 밖은 추가 불가. 추가하려면 사용자 승인)

- `C:\Windows\Temp\*` (내용물만. 폴더 자체는 유지) — 관리자 권한 필요
- `C:\Windows\SoftwareDistribution\Download\*` — 관리자 권한 필요, Windows Update 서비스가 사용 중이면 건너뜀
- `C:\Windows\Logs\CBS\*.log` 등 오래된 로그 (규칙에 명시된 패턴만)
- `C:\Windows\Prefetch\*` 는 **정리 대상에서 제외** (성능에 영향. 기본 비활성, 규칙에 넣지 않는다)
- `C:\Windows.old` — 대용량이지만 `caution`: 사용자가 명시 선택 + 확인 시. 일반적으로 Windows 디스크 정리 호출을 권장 (직접 삭제 시 권한 문제 큼)
- `%LOCALAPPDATA%\Temp\*`
- `%LOCALAPPDATA%\Microsoft\Windows\Explorer\thumbcache_*.db`
- 브라우저 **캐시** 폴더(`Cache`, `Code Cache`, `GPUCache` 등)만. 프로필/쿠키/로그인 데이터 제외
- 개발 도구 캐시: npm cache, pip cache, gradle caches, NuGet http-cache 등 (규칙 시드 참고)
- 크래시 덤프: `%LOCALAPPDATA%\CrashDumps\*`, `C:\Windows\Minidump\*`
- GPU 셰이더 캐시: `%LOCALAPPDATA%\D3DSCache`, `%LOCALAPPDATA%\NVIDIA\DXCache`, `%LOCALAPPDATA%\NVIDIA\GLCache`, `%LOCALAPPDATA%\AMD\DxCache` (게임 첫 실행이 잠깐 느려질 뿐 재생성됨. 기본 선택 해제)
- VS Code 캐시: `%APPDATA%\Code\` 아래 `Cache`, `Code Cache`, `CachedData`, `GPUCache` (설정/확장 프로그램 폴더는 제외)
- 휴지통(`C:\$Recycle.Bin`): **파일을 직접 삭제하지 않고** `specialAction: empty-recycle-bin`(시스템 API)으로만 처리
- `C:\Windows.old`: `specialAction: run-disk-cleanup`(Windows 디스크 정리 호출)으로만 처리. 앱이 직접 `fs.rm` 하지 않는다

> 참고: §3.1에서 "루트 자체"/"자체"로 표기한 항목(`C:\Users`, `C:\Users\<사용자>`, `AppData\Local|Roaming|LocalLow`)은 **그 폴더 자체만** 삭제 불가라는 뜻이다. 그 하위는 규칙 DB(위 열거 범위)와 나머지 보호 목록이 판정하며, 규칙이 없는 하위는 `unknown`이라 역시 삭제할 수 없다.

각 항목의 정확한 패턴과 안전도는 `resources/cleanup-rules.json`이 정의한다. 이 규칙 파일이 위 열거 범위를 벗어나는 항목을 포함하면 로더가 **로딩 시점에 거부**하고 경고한다 (검증기: `rules/validate.ts`).

## 6. 프로그램 제거 정책

- 제거는 **해당 프로그램의 공식 제거 프로그램 실행**으로만 한다 (`UninstallString`/`QuietUninstallString`).
- 앱이 `Program Files` 등의 폴더를 직접 삭제하는 기능은 만들지 않는다. 강제 삭제 없음.
- 제거 전 확인 대화상자 필수 (이름, 게시자, 용량).
- 프로그램 규칙 안전도:
  - `protected`: 제거 버튼 비활성 (예: GPU 드라이버, 칩셋/오디오 드라이버, 보안 소프트웨어 핵심 구성요소, Windows 구성요소)
  - `caution`: 제거 가능 + 경고 문구 (예: Visual C++ 재배포 패키지 — 다른 프로그램이 의존할 수 있음, .NET 런타임, Java 런타임)
  - `safe`/`unknown`: 제거 가능 (일반 사용자 앱). 단 시스템 컴포넌트(`SystemComponent=1`)는 기본 목록에서 숨기고 토글로만 표시, 제거 버튼은 `caution` 취급.
- 실행할 명령은 `UninstallString`만 사용한다. `QuietUninstallString`(화면 없는 자동 제거)은 사용하지 않는다. 관리자 권한을 요구하는 제거 프로그램은, 일반 실행이 권한 오류(`UNKNOWN`/`EACCES`/`EPERM`)로 시작조차 못 할 때만 **같은 명령 그대로** UAC(`Start-Process -Verb RunAs`)로 다시 실행한다 (9단계 결정). UAC 를 거부하면 "시작하지 않았다"고 알리고 끝낸다.
- 제거 프로그램 명령줄은 **레지스트리에서 읽은 값을 그대로 실행하되**: 셸 인젝션 방지를 위해 `shell: false` + 인자 분리 파싱, 실행 전에 실행 파일이 존재하는지 확인. 알 수 없는 형식이면 거부.
- (9단계 구현) 파서는 `src/main/programs/command.ts` 의 순수 함수이며 **알려진 안전한 형태만** 통과시킨다: 드라이브 절대경로의 실제로 존재하는 `.exe`(따옴표 유무 무관, 따옴표 없는 공백 경로는 존재하는 `.exe` 경계가 정확히 하나일 때만), 셸·스크립트 호스트·시스템 도구(cmd, powershell, wscript, mshta, rundll32, regsvr32, reg …) 거부, UNC/장치/상대경로/`..`/`%`/대체 스트림/끝 공백·점 거부, 인자에 `& | ; < > ^ % ! \` $ * ?` 와 `\"` 이스케이프 거부, 제어문자·길이·인자 수 제한, msiexec 는 `/X{GUID}`·`/I{GUID}` 만 허용하고 실행 파일을 시스템 폴더의 msiexec.exe 로 고정. 실행은 `spawn(exe, args, { shell: false })`.
- (9단계 구현) 제거도 삭제와 같은 `ConfirmationStore` 의 일회용 확인 토큰을 쓴다(계획 단계의 명령과 실행 시점의 명령이 다르면 거부). protected 는 계획과 실행 양쪽에서 거부, caution·규칙 없는 시스템 구성요소는 경고 확인(`acknowledgeCaution`) 필수. 시작 로그를 쓰지 못하면 실행하지 않는다.
- 제거 후 남는 폴더는 "남은 폴더 후보"로 **보여주기만** 하고, 삭제는 §4 조건을 다시 통과해야 한다.

## 7. 관리자 권한 정책

- 앱은 **일반 권한**으로 시작한다. `requestedExecutionLevel`은 `asInvoker`.
- 관리자 권한이 필요한 정리 항목(`requiresAdmin: true`)은 실행 시점에 사용자에게 설명하고 UAC 상승을 요청한다.
- 상승은 **정리 전용 헬퍼 프로세스**(별도 인자로 재실행 또는 별도 실행 파일)에서만 하고, 헬퍼는 §3 보호 경로 검사와 §4 조건을 **자체적으로 다시** 수행한다 (renderer/main을 신뢰하지 않는다).
- 헬퍼는 전달받은 "정리 항목 ID 목록 + 확인 토큰"만 받고, 임의 경로 삭제 요청을 받지 않는다. (경로는 헬퍼가 규칙 DB에서 직접 해석)
- 사용자가 UAC를 거부하면 해당 항목은 건너뛰고 결과에 "권한 거부"(`admin-declined`)로 기록.
- (8단계 구현) 헬퍼는 하드코딩 허용 목록(`win-system-temp`, `win-minidump`, `win-cbs-logs`, `win-update-download`)의 규칙 ID만 받는다. job 은 서명(HMAC)·토큰 해시·유효 시간(2분)을 검증하고, 경로 필드가 있거나 허용 목록 밖 ID이면 아무것도 지우기 전에 거부한다. 환경변수는 믿지 않고(SystemRoot 검증), 영구 삭제 설정은 헬퍼가 설정 파일에서 직접 읽는다. 자세한 신뢰 모델과 한계는 ARCHITECTURE.md §7.2.
- 스캔은 관리자 권한 없이 동작해야 한다. 권한이 없는 폴더는 건너뛴 항목으로 표시.

## 8. 삭제 실행 방식

| 모드           | 사용 조건                                             | 구현                                                                                                                                                                             |
| -------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `trash` (기본) | 모든 허용 대상                                        | Electron `shell.trashItem` 사용 (또는 동등한 휴지통 API). 휴지통으로 못 보내는 경우(용량이 너무 큼, 네트워크 경로 등)는 실패로 보고하고 자동으로 영구 삭제로 전환하지 **않는다** |
| `permanent`    | 카테고리 `temp`/`cache` + 설정에서 허용 + 사용자 확인 | `fs.rm` 계열. 폴더 자체가 아니라 **내용물**만 삭제하는 규칙은 폴더를 남긴다                                                                                                      |

- 휴지통으로 이동한 파일은 휴지통을 비우기 전까지 디스크 공간이 늘지 않는다. 결과 화면에 "휴지통을 비워야 실제 용량이 늘어납니다"를 반드시 안내한다.
- 사용 중인 파일(EBUSY/EPERM)은 건너뛰고 집계. 강제 종료/핸들 해제 같은 행위 금지.
- 대량 삭제는 취소 가능해야 한다. 취소 시 이미 지운 것은 기록에 남기고 나머지는 중단.
- 삭제 도중 오류가 나도 전체를 중단하지 않고 항목별 결과를 기록한다 (단, 안전 검사 실패는 즉시 해당 항목 거부).
- 휴지통 비우기는 별도 정리 항목(`recycle-bin`)으로 두고, 이 경우만 시스템 API를 통해 수행한다.

## 9. 사용자 확인 UX 규칙

- 확인 대화상자에는 반드시: 삭제할 항목 수, 총 용량, 방식(휴지통/영구), 가장 큰 3개 항목 경로, `caution` 항목이 있으면 그 경고 문구.
- 영구 삭제는 별도 강조 + "되돌릴 수 없음" 문구 + 체크박스 확인.
- 확인 버튼 기본 포커스는 "취소"에 둔다.
- "다시 묻지 않기" 옵션 금지 (삭제 확인에 대해서는).
- 원클릭 안전 정리도 확인 단계를 건너뛰지 않는다.

## 10. 로그

- 위치: 앱 사용자 데이터 폴더의 `logs/cleanup-YYYY-MM-DD.log`.
- 기록: 타임스탬프, 작업 종류(삭제/제거), 대상 경로, 방식, 결과(성공/건너뜀/거부/오류), 사유.
- 안전 검사에서 거부된 요청도 기록한다 (버그/악용 탐지용).
- 로그는 외부로 전송하지 않는다.

## 11. 개발 중 안전 규칙 (Claude Code용)

- 삭제 로직 테스트는 **오직** `tests/fixtures/`가 만드는 임시 디렉터리(`os.tmpdir()` 하위 고유 폴더)에서만 한다.
- 테스트에서 보호 경로 검사를 비활성화하는 플래그를 **프로덕션 코드에 만들지 않는다.** 대신 검사 함수에 "허용 루트"를 주입(의존성 주입)해서 테스트 루트를 허용 루트로 넘기는 방식을 쓴다.
- 실제 `C:\Windows`, `C:\Users` 등에 대해 `fs.rm`, `shell.trashItem`, 제거 프로그램 실행을 호출하는 코드를 개발/CI/테스트 중에 실행하지 않는다. 실제 환경에서의 수동 검증은 사용자가 직접 한다.
- 새 삭제 코드 경로를 추가하면 반드시 §4 체크리스트 각 항목에 대한 **거부 테스트**(실패해야 하는 케이스)를 함께 추가한다.

## 12. 체크리스트 (삭제/제거 관련 PR 전)

- [ ] 모든 삭제가 `safety` 모듈의 단일 관문을 거친다.
- [ ] 보호 경로 거부 테스트가 있고 통과한다 (직접 경로, `..` 우회, 짧은 이름, 정션 우회 포함).
- [ ] `unknown`/`protected` 거부 테스트가 있다.
- [ ] 접두사 경계(`C:\Temp` vs `C:\Temp2`) 테스트가 있다.
- [ ] 휴지통 기본, 영구 삭제는 조건부임을 테스트로 확인했다.
- [ ] 확인 토큰 없는 요청이 거부된다.
- [ ] UI에서 `protected`/`unknown` 항목의 삭제 버튼이 없거나 비활성이다.
- [ ] 로그가 남는다.
- [ ] 관리자 헬퍼가 자체적으로 재검증한다 (해당 시).
